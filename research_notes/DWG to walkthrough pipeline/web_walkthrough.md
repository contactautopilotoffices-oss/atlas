## Q1. Real-time three.js first-person walk: collision, navmesh, click-to-teleport, guided tours, starter repos

### Takeaway
For a single static office floor, the lightest robust option is a **three-mesh-bvh capsule controller**: a capsule shapecast against a merged, BVH-indexed collision mesh. It is MIT, actively released (0.9.18, 3 Nov 2026), and three.js-native. Add a **pre-baked navmesh (recast-navigation-js, MIT, 0.44.0, 30 Oct 2026)** only if you need click-to-walk pathfinding or "walk me to the boardroom" routing. A physics engine (Rapier, about 15 MB unpacked on npm) is overkill for a walk-only tour. Guided tours are camera-path work (CatmullRom curve or camera-controls), not a library choice.

### Cited Findings
- three-mesh-bvh: latest **0.9.18, published 2026-11-03, MIT** — [npm registry](https://registry.npmjs.org/three-mesh-bvh)
- three-mesh-bvh ships a "Player movement" example ([characterMovement.html](https://gkjohnson.github.io/three-mesh-bvh/characterMovement.html)), a shapecast example ([shapecast.html](https://gkjohnson.github.io/three-mesh-bvh/shapecast.html)) and a sphere-physics collision example ([physics.html](https://gkjohnson.github.io/three-mesh-bvh/physics.html)). The BVH is static: moving vertices need `refit`, and other geometry changes need a rebuild — [three-mesh-bvh README](https://github.com/gkjohnson/three-mesh-bvh)
- The characterMovement example source uses a capsule built from a `RoundedBoxGeometry` and a line `segment`, and resolves collisions with `bvh.shapecast(...)`. This is the standard capsule-vs-static-level pattern — [characterMovement.js](https://github.com/gkjohnson/three-mesh-bvh/blob/master/example/characterMovement.js)
- three.js core includes an FPS example (`games_fps.html`) that uses the addons `Octree` and `Capsule` (`capsuleIntersect`) for collision against a level GLB with no extra dependency — [three.js examples/games_fps.html](https://github.com/mrdoob/three.js/blob/dev/examples/games_fps.html)
- three.js dev also ships `webgl_batch_lod_bvh`, which uses three-mesh-bvh with `@three.ez/batched-mesh-extensions` (BatchedMesh, 500k instances, 5 LODs generated with meshoptimizer, BVH-accelerated culling and raycasting). This is relevant if furniture is instanced — [three.js examples/webgl_batch_lod_bvh.html](https://github.com/mrdoob/three.js/blob/dev/examples/webgl_batch_lod_bvh.html)
- recast-navigation-js is a WASM port of Recast/Detour. It offers navmesh generation in the browser **or Node** (solo, tiled and TileCache generators), path queries, closest point, raycasts, crowds, off-mesh links, and three.js and PlayCanvas integrations. It can **export/import navmeshes as Uint8Array**, which allows offline generation and runtime import. The README suggests offline generation for static environments and shows a glTF-Transform CLI custom-command route for asset pipelines. Licence MIT — [recast-navigation-js README](https://github.com/isaac-mason/recast-navigation-js)
- recast-navigation 0.44.0 (2026-10-30, MIT). `@recast-navigation/wasm` unpacked size is about 2.0 MB on npm — [npm registry recast-navigation](https://registry.npmjs.org/recast-navigation); [npm @recast-navigation/wasm](https://registry.npmjs.org/@recast-navigation/wasm/latest)
- The same README points to **navcat**, a pure-JS library using the same Recast/Detour algorithms, for cases where WASM size does not fit the budget. navcat latest is 0.4.1 (2026-05-06, MIT) — [recast-navigation-js README](https://github.com/isaac-mason/recast-navigation-js); [npm navcat](https://registry.npmjs.org/navcat)
- Isaac Mason's NavMesh Generator website builds a navmesh from an uploaded model, for simple projects — [recast-navigation-js README](https://github.com/isaac-mason/recast-navigation-js) (links navmesh.isaacmason.com)
- three-pathfinding (Don McCurdy) latest is **1.3.0, 2024-05-17**, MIT. No release in about 2.5 years, and it needs a navmesh authored elsewhere — [npm registry](https://registry.npmjs.org/three-pathfinding)
- Rapier JS (`@dimforge/rapier3d-compat`) latest is 0.21.0 (2026-09-25), Apache-2.0, unpacked npm size about 15 MB (WASM inlined in the compat build) — [npm registry](https://registry.npmjs.org/@dimforge/rapier3d-compat/latest)
- cannon-es latest is **0.20.0, 2022-08-12**, MIT. It is effectively unmaintained — [npm registry](https://registry.npmjs.org/cannon-es)
- camera-controls (yomotsu) is 3.1.2 (2025-11-17, MIT). It is commonly used for smooth `setLookAt`/`fitToBox` transitions between tour stops — [npm registry](https://registry.npmjs.org/camera-controls)
- @react-three/drei is 10.7.9 (2026-09-25, MIT). It is React-only, so it does not fit a vanilla vendored-three site without adopting R3F — [npm registry](https://registry.npmjs.org/@react-three/drei)

### Inferences
- **Recommended stack for this site** (vanilla three.js, static Vercel):
  1. In Blender, author a simplified, invisible **collision mesh**: walls, glazing, columns, desks as boxes, and a floor. Export it to a separate small GLB, or as a named node.
  2. At runtime, run `MeshBVH` on the merged collision geometry, with a capsule (radius about 0.25 m, height about 1.7 m) and gravity. Copy the characterMovement example. Alternatively, use the zero-dependency `Octree` + `Capsule` from three.js `games_fps`. Both work. Octree is already in three.js addons, but it is not vendored in r169 here, so it must be copied in. three-mesh-bvh is faster for raycasts and teleport picking.
  3. **Click-to-teleport**: raycast (BVH-accelerated) against the floor mesh. Accept a hit only if the hit normal points up and the point is on the navmesh (or inside a floor-polygon whitelist). Then tween the camera.
  4. **Guided tour**: author camera-path empties or a curve in Blender, export them as glTF nodes or animation, and play them with `CatmullRomCurve3` and lookAt targets, or with camera-controls transitions between "stops". The same stops double as 360-panorama positions (see Q3), so the 3D and image-based modes can share a hotspot graph.
  5. Use a **navmesh only if** you want click-anywhere pathing or "walk me to X". Generate it **offline in Node 22** with recast-navigation (it supports Node) and ship the exported binary. This avoids generation at runtime. For a single floor plate, a hand-drawn floor polygon in Blender, exported as a mesh, is often enough.
- Physics (Rapier/cannon) adds megabytes and tuning for no walk-tour benefit. Skip it unless doors or props must be physically interactive.
- Mobile: pointer-lock FPS controls do not exist on touch devices. Plan **tap-to-teleport plus drag-to-look** as the default on phones, and keep WASD/pointer-lock as a desktop option.

## Q2. Photoreal in the browser: baked lightmaps, probes, HDR environment, AO, postprocessing, budgets and compression

### Takeaway
Browser interior realism comes overwhelmingly from **baked global illumination**. This means baking Cycles lighting (diffuse GI, AO, soft shadows from windows and fixtures) into lightmaps on a second UV set, then adding a cheap real-time layer: an HDR or cube environment for reflections, optional screen-space AO (N8AO or GTAO), tone mapping and a light bloom. glTF has no standard lightmap slot and three.js GLTFLoader parses no lightmap extension, so expect a small custom loader step. Ship geometry with meshopt and textures as KTX2 (UASTC for normal maps, ETC1S for colour and lightmaps) via glTF-Transform. All of this runs on a headless CPU Linux box.

### Cited Findings
**Baking and lightmaps**
- glTF has no native lightmap slot. Common workarounds are wiring the bake into Blender's emission input, or exporting the lightmap separately and assigning it in three.js. three.js uses the second UV set for lightMap/aoMap. glTF lightmaps typically need `flipY = false` (search-result summary of three.js forum threads; forum itself unreachable) — [three.js forum: Apply UV coordinates and lightmaps baked from Blender](https://discourse.threejs.org/t/apply-uv-coordinates-and-lightmaps-baked-from-blender-to-mesh/63910); [forum: Blender glb export secondaryUV](https://discourse.threejs.org/t/blender-glb-export-secondaryuv/60245)
- Since the introduction of `Texture.channel` (default 0), three.js lets any map pick its UV set. Set `lightMap.channel = 1` for TEXCOORD_1 — [three.js src/textures/Texture.js](https://github.com/mrdoob/three.js/blob/dev/src/textures/Texture.js)
- The three.js GLTFLoader (dev) registers KHR_materials_* (incl. anisotropy, diffuse_roughness, dispersion), KHR_texture_basisu, EXT_texture_webp/avif, EXT_ and **KHR_meshopt_compression**, KHR_draco, KHR_mesh_quantization, EXT_mesh_gpu_instancing and KHR_lights_punctual. It has **no lightmap extension** (no MOZ_lightmap handling) — [three.js GLTFLoader.js](https://github.com/mrdoob/three.js/blob/dev/examples/jsm/loaders/GLTFLoader.js)
- Mozilla's hubs-blender-exporter extends Blender's glTF exporter with **MOZ_lightmap**: a "MOZ_lightmap" shader node takes the lightmap image, and a UV Map node selects the set. It warns that the second UV set must be used because three.js was hardcoded to it (older note) — [hubs-blender-exporter README](https://github.com/MozillaReality/hubs-blender-exporter). Mozilla's "EZ-Bake" lab post covered the same Blender bake-to-Hubs flow — [Hubs Labs: EZ-Bake Lightmapping](https://hubs.mozilla.com/labs/ez-bake-lightmapping/)
- **The Lightmapper** (Naxela) is a Blender add-on for Cycles-based GI lightmap baking with 32-bit HDR lightmaps. It automates UV unwrap, layering and material setup, offers per-object resolution and margin, OIDN CPU or OptiX denoising, OpenCV post-filtering, background baking, and "baking without material setup for external engines" — [The_Lightmapper README](https://github.com/Naxela/The_Lightmapper). Its README advertises "Version 0.3", and its compatibility with Blender 5.x was not verified.
- Needle Engine documents a Blender lightmapping workflow for web export (commercial engine on top of three.js) — [Needle docs: Blender lightmapping](https://engine.needle.tools/docs/blender/lightmapping) (search result only)
- Shapespark, a commercial reference product for this exact use case, delivers WebGL browser walkthroughs whose "lighting is baked to provide a high level of realism and good presentation time performance". It takes Blender via GLB (recommended), with its own baker on CUDA or multi-CPU cloud. A staff member said the Blender render engine doesn't matter: just UV-map everything — [Shapespark homepage](https://shapespark.com/); [Shapespark Rhino import guide](https://help.shapespark.com/hc/en-us/articles/37153733939101-Import-a-3D-model-from-Rhino); [Shapespark forum: Blender workflow tips](https://forum.shapespark.com/t/optimizing-exterior-and-interior-models-workflow-tips-for-blender-and-shapespark/4765)
- A Verge3D tutorial states real-time browser interiors are impractical without baking lighting into textures. A Codrops case study notes baked shadows in the GLB avoided dynamic shadow maps for performance — [cgbookcase: Blender & Verge3D](https://www.cgbookcase.com/learn/how-to-create-3d-interactive-web-experiences-in-blender-verge-3d); [Codrops: Windland case study](https://tympanus.net/codrops/2022/04/25/case-study-windland-an-immersive-three-js-experience/)
- Other baking walkthroughs: [svilenkovic: how to bake lighting for web](https://svilenkovic.com/3d/how-to-bake-lighting-for-web); [Baked lighting in R3F](https://blog-54a.pages.dev/baked-lighting-in-r3f); [Packt Learn Three.js ch.13 Blender lightmaps/AO](https://subscription.packtpub.com/book/web-development/9781803233871/17/ch17lvl1sec78/B18726_10.xhtml); [Three.js Journey: creating a scene in Blender (baked)](https://www.threejs-journey.com/lessons/creating-a-scene-in-blender)

**New three.js lighting primitives (dev examples, Nov 2026; check whether they are in the r187 tag before relying on them)**
- `LightProbeGridWebGL` (addons/lighting) gives a "light probe volume: position-dependent diffuse global illumination via an L2 SH probe grid". **AO and postprocessing**
- **N8AO** 2.0.1 (2026-08-10, ISC) is a drop-in AO pass for three.js EffectComposer and pmndrs/postprocessing. - three-gpu-pathtracer 0.0.28 (2026-11-02, MIT) gives progressive path tracing in the browser. It suits still "photo mode" captures, not walking — [npm](https://registry.npmjs.org/three-gpu-pathtracer)

**Compression and budgets**
- glTF-Transform CLI 4.5.1 (2026-09-28, MIT): `optimize` (all-in-one), `meshopt --level medium`, `draco`, `resize`, `webp`, and KTX2/Basis via `uastc` (e.g. normal/occlusion/metalRough, `--level 4 --rdo --zstd 18`) and `etc1s --quality 255` — [glTF-Transform CLI README](https://github.com/donmccurdy/glTF-Transform/blob/main/packages/cli/README.md); [npm](https://registry.npmjs.org/@gltf-transform/cli)

- meshoptimizer 1.3.0 (2026-09-25, MIT) — [npm](https://registry.npmjs.org/meshoptimizer). GLTFLoader now accepts both EXT_meshopt_compression and KHR_meshopt_compression — [GLTFLoader.js](https://github.com/mrdoob/three.js/blob/dev/examples/jsm/loaders/GLTFLoader.js)

### Inferences
- **Pipeline that fits the build box (headless Linux, CPU, bpy, Node 22):**
  1. In bpy, add a second UV map, `lightmap`, via Smart UV Project or Lightmap Pack with margin. Pack big surfaces (floor, ceiling, walls) into one or a few atlases. Furniture can use per-object small lightmaps or AO-only.
  2. Cycles **CPU bake** of type `DIFFUSE` with direct+indirect, colour pass off (irradiance only) to keep albedo separate and tileable. Alternatively, bake `COMBINED` for "what you see is the render", at the cost of re-baking whenever materials change. Use OIDN denoise (CPU) on the baked image. The Lightmapper automates this if it works headless on Blender 5.x (unverified).
  3. Export GLB with both UV sets. In three.js, after load, assign `material.lightMap = tex; tex.channel = 1; tex.flipY = false; tex.colorSpace` per encoding. Set `lightMapIntensity`, and reduce or disable dynamic lights. Drive the mapping from `mesh.userData` (glTF extras from Blender custom properties) to avoid a custom extension. MOZ_lightmap is an option, but GLTFLoader would need a plugin to read it.
  4. HDR lightmaps: 8-bit sRGB PNG/KTX2 is usually acceptable for indoor office lighting. If window blowout or night scenes need range, use RGBM or half-float EXR/HDR (heavier). KTX2 ETC1S on lightmaps can band, so prefer UASTC for lightmaps on gradients.
  5. Reflections: one `PMREM` from a Blender-rendered or HDRI equirect for the floor (or a CubeCamera capture per room). Box projection exists only in WebGPU examples today. For WebGL r169, glossy floors and glass will reflect "infinitely far" unless a custom shader chunk is used.
  6. Post: tone mapping (ACES or AgX; Blender's AgX view transform is the default, so match it), N8AO at "Performance/Low" + halfRes on phones and "Medium" on laptops, subtle bloom on emissive fixtures, and SMAA/MSAA. GTAOPass is already vendored in r169. Baked AO plus N8AO can double-darken, so use one or tune them together.
- **Indicative budgets** (inference; no authoritative source gathered): aim for under about 15–25 MB total first load for one office floor on phones. That means 2–4 lightmap atlases at 2048² (KTX2), shared tiling material textures at 1k, geometry meshopt'd to a few MB, and progressive loading of furniture. Keep draw calls under a few hundred via merging or `BatchedMesh`/instancing for chairs and desks.
- Upgrading the vendored three.js from r169 to r18x would bring KHR_meshopt_compression support, newer light probe tooling and the WebGPU path. It is not required for baked lightmaps, which work on r169.

## Q3. Image-based alternatives: 360 panorama hotspot tours, video flythrough, Gaussian splatting

### Takeaway
- **Cycles-rendered 360° panoramas** linked as a hotspot tour give the **highest fidelity per effort** and run on any phone. All three viewers are MIT/Apache, and Photo Sphere Viewer (three.js-based, actively released) fits best.
- **Gaussian splats** are now well served in three.js by **Spark** (MIT, World Labs; v2.4.0 on 20 Oct 2026, with LoD and streaming since 2.0). Training is the bottleneck. Mainstream trainers (gsplat, nerfstudio, LichtFeld) require CUDA. **OpenSplat** can train CPU-only, but its README says about 100x slower and it is AGPLv3. On a CPU-only box, splats are feasible but slow; rent a GPU for training instead.
- A **pre-rendered video flythrough** is the cheapest interactive-free option: Cycles CPU renders, MP4/WebM, no library.

Multires tile generator `utils/multires/generate.py` needs Hugin's `nona` — [Pannellum README](https://github.com/mpetroff/pannellum). Latest npm **2.5.7, 2026-02-19** — [npm](https://registry.npmjs.org/pannellum)
- **Marzipano** (Google, "not an official Google product"): Apache-2.0. Latest npm **0.10.2, 2021-03-18**, so it is dormant — [Marzipano README](https://github.com/google/marzipano); [npm](https://registry.npmjs.org/marzipano)

- **gsplat** (nerfstudio): "CUDA accelerated rasterization", PyTorch 2.7+, CUDA 12.8/13 — [gsplat README](https://github.com/nerfstudio-project/gsplat). PyPI 1.5.3 (2025-07-04) — [PyPI](https://pypi.org/pypi/gsplat/json). **nerfstudio** PyPI 1.1.5 (2024-11-11, Apache-2.0) — [PyPI](https://pypi.org/pypi/nerfstudio/json)
- **Brush**: trains via WebGPU (Burn) on macOS/Windows/Linux, AMD/NVIDIA/Intel, Android and in-browser. It takes COLMAP or nerfstudio data. It needs a GPU (WebGPU), not CPU — [Brush README](https://github.com/ArthurBrussee/brush)
- **LichtFeld Studio**: GPLv3. Requires an NVIDIA GPU (compute capability 7.5+, driver 570+, CUDA 12.8+) — [LichtFeld README](https://github.com/MrNeRF/LichtFeld-Studio)

### Inferences
- **360 tour from Blender (best fidelity per effort):** In bpy, add a panoramic camera (Cycles equirectangular) at each tour stop at eye height (about 1.6 m). Render at 8192×4096 on CPU with OIDN denoise. Expect long CPU renders per pano; time this on the box. Load them in **Photo Sphere Viewer + VirtualTourPlugin**: it is three.js-based, MIT and current, and nodes, links and markers map to rooms and hotspots. Pannellum is the tiny alternative if three.js integration doesn't matter, but its multires tiler needs Hugin `nona`. Avoid Marzipano (no release since 2021). Because the renders are path-traced, glass, reflections and GI are exact. The cost is no free movement, only "jump" transitions; the fade or zoom between nodes feels like Matterport.
- **Hybrid (recommended for a sales page):** reuse the same Blender camera stops as (a) 360 panos for "photo-real mode" and (b) teleport targets in the lightmapped real-time walk. Use (c) the real-time walk's floor plan and minimap for orientation. This mirrors the "hybrid 360 tours" pattern in the forum thread title.
- **Splats from Blender renders:** this is technically clean because camera poses are known exactly (BlenderNeRF → nerfstudio `transforms.json`, which OpenSplat and Brush accept). But: (1) OpenSplat needs sparse points, so you must sample points from the mesh or run COLMAP with known poses. (2) CPU training is about 100x slower, so a 30k-iteration interior could take many hours to days on CPU (extrapolation, unmeasured). (3) Hundreds of Cycles CPU renders are needed as input, which is a larger render cost than about 10 panoramas. (4) **AGPLv3** applies to OpenSplat the tool, not the output. Conclusion: splats from synthetic renders add little over panoramas plus a lightmapped mesh for a model you already own. Splats make most sense for **photo captures of the real fitted floor** (then: rent a GPU, or use a hosted trainer). View them with Spark, convert and compress with splat-transform (SOG or streamed LOD), and use its voxel output or a separate collision mesh for walking.
- **Video flythrough:** render Cycles frames along the same guided-tour path, encode H.264/H.265 + WebM, and use a `<video>` with chapter buttons. Zero runtime risk, best for phones and social, but no interactivity. Good as a fallback or poster for the 3D mode.

## Q4. Architectural walkthrough sites done in three.js: what they used, and fidelity vs. interactivity vs. effort

### Takeaway
Published three.js archviz walkthroughs almost all share one recipe: **Blender/3ds Max model → baked lighting (lightmaps or full combined bakes) → GLB → three.js with minimal dynamic lights, plus env-map reflections and light post**. Commercial products that do this end-to-end (Shapespark, Needle, Verge3D) confirm the pattern. Splats and 360 panos are the main alternatives when fidelity matters more than free movement. Verifiable, detailed public case studies are scarce, and most are vendor marketing.

### Cited Findings

- For a **property sales page** whose goal is persuasive realism on phones, approach **B (or E)** maximises perceived quality per hour of work on a CPU-only box. Approach **A** is the right extension of the existing dollhouse + walk explorer (same vendored three.js, same controls).
